# OmniDesk 系统设计原则与设计方案 v0.3

> 状态：FROZEN（项目宪法）  
> 适用：OmniDesk 全系列产品与所有协同 AI 模型（Codex / Claude / Gemini）

---

## 一、项目定位

### 项目名称
OmniDesk

### 当前产品
OmniDesk Discipline

### 产品定位
> 面向纪检监察综合履职场景的 AI 工作站。

- 不是通用 AI 助手
- 不是 AI 聊天工具
- 不是自动决策系统

**核心目标：**
利用 AI 显著提升：
1. 材料生产效率；
2. 知识获取效率；
3. 工作经验沉淀效率。

---

## 二、总体架构原则

### 原则 1：先产品，后平台
当前阶段：
- 不建设通用 AI 平台。
- 优先验证：**一个真实用户、一个真实领域、一个真实工作流**。
- **严禁提前开发**：Agent 市场、插件生态、多用户平台、通用工作流引擎。
- 未来演化路线：只有当第二、第三个 Workstation 成熟后，再向上抽象 OmniDesk Core。

---

## 三、技术架构原则

### 原则 2：DSH 作为 Runtime，不作为业务层

```yaml
DSH Runtime
      │
      ▼
OmniDesk Profile
      │
      ▼
Workstation
      │
      ▼
Skills
      │
      ▼
Local Data
```

**绝对禁止修改：**
- DSH 核心代码；
- DSH 运行机制；
- DSH 升级逻辑。

**所有业务扩展必须通过：**
- Profile 配置补丁；
- Skill 声明；
- 外部配置文件；
- 外部数据目录。

## 四、核心概念定义

### 1. Workstation (工作站)
定义：一个具体业务领域的工作环境。
例如：`workstations/discipline/`
包含：
```
discipline/
├── profile.yaml
├── skills/
├── knowledge/
├── templates/
└── memory/
```
Workstation 负责：领域配置、技能组合、数据目录映射。

### 2. Skill (技能)
定义：单一、可复用的专业能力。
特点：无状态、单一职责、不保存业务数据。
例如：`material-writing`、`knowledge-search`、`document-review`
Skill 负责：“怎么做”。

### 3. Agent (智能体)
当前阶段弱化。
定义：多个 Skill 的任务组合。
当前策略：不主动开发复杂 Agent，仅在出现多步骤固定业务流时再做组合封装。

---

## 五、数据设计原则

### 原则 3：数据资产独立于 AI 运行环境
AI 模型与运行工具会变，业务与个人资产必须长期存在。
统一外部数据中枢：
```
~/OmniDesk/
├── workspaces/
├── knowledge/
├── templates/
├── memory/
├── projects/
└── backups/
```

### 数据分级保护原则
- **一级（公开数据）**：法规公开文件、通用知识。允许云端模型处理。
- **二级（内部资料）**：内部制度、工作材料。优先本地模型或合规专有模型。
- **三级（敏感资料）**：案件线索、未公开调查材料。**绝对禁止进入个人 AI 系统**。

## 六、OmniDesk Discipline v0.1 功能范围

### 第一优先级（P0）
1. **Skill 1：材料写作助手**
   - 目标：提升纪检材料生产效率（工作总结、汇报材料、调研报告、交流发言、理论学习心得）。
   - 流程：素材输入 → 模板选择 → 结构生成 → 初稿生成 → 人工修改 → 模板沉淀。
   - 核心资产：不仅是文本，更是个人写作方法库与套路模板。
2. **Skill 2：知识库助手**
   - 目标：实现可靠知识查询。
   - 强约束：所有回答必须包含：**答案 + 原文引用 + 来源文件 + 具体位置**。严禁无来源脑补。

### 第二优先级（P1）
3. **Skill 3：会议整理助手**
   - 输入：会议记录文本、初转录文本。
   - 输出：会议纪要、任务清单。
   - 未来扩展：连接 V2T 语音处理管道。

---

## 七、暂不实现功能清单（明确禁止）
1. 自动纪律判断（高风险）
2. 案件审理 Agent（未来仅考虑文书格式检查）
3. 监督检查 Agent（涉及敏感数据）
4. OmniDesk Core 通用抽象（过度设计）
5. Agent Registry / Marketplace（过度设计）
6. 自研 GUI（直接复用 DSH 现成桌面视窗与 Web 界面）

---

## 八、版本升级原则（Golden Tasks 守门）
DSH 升级必须通过基线验证。
在 `tests/golden_tasks/` 保存 20-30 个真实场景脱敏任务。
任何底座升级前，必须跑通：
- Profile 加载测试
- Skill 调度测试
- 文件读取与上下文加载测试
- 输出格式与引用准度测试
- 数据保存与备份测试

---

## 九、成功度量标准（Discipline v0.1）
1. 材料生产耗时降低 ≥ 20%
2. 知识查询可靠性：引用准确率 ≥ 90%
3. 形成个人持续积累的模版与知识资产
