# Superpowers 方法分析与 OmniDesk 适配建议

> 研究对象：https://github.com/obra/superpowers（2026-11-04 克隆 main 快照到 /private/tmp/sp-research，仅阅读研究，未安装、未引入任何内容）。
> 本文区分三类内容：**已验证事实**（实读仓库文件所得）、**研究结论**（对照分析）、**建议**（待用户批准后进入工程规范的草案内容）。

## 一、仓库真实结构（已验证事实）

- `skills/` 下共 15 个技能，每个技能一个目录 + `SKILL.md`，部分带 `references/` 辅助文件。核心技能：brainstorming、writing-plans、executing-plans、subagent-driven-development、test-driven-development、systematic-debugging、verification-before-completion、using-git-worktrees、requesting-code-review、receiving-code-review、finishing-a-development-branch 等。
- 全部机制是"提示词技能"而非工具：靠 SKILL.md 的指令约束模型行为，仓库自身没有运行时强制手段。规范是否生效取决于模型是否读到并遵守。

## 二、核心方法逐项分析

### 1. Brainstorming（需求澄清）

**事实：** 流程为「先读项目材料 → 第一条消息回显需求并指出冲突/约束 → 若有多种合理方案则列对比让用户选 → 写设计文档 → 批准后才进入 writing-plans」。明确要求 "Look Before You Ask"：不问项目已回答的问题，一次只问一个最关键的问题。

**研究结论：** 与 OmniDesk 现行「先读 Git 状态与代码 → 分类需求 → 写 PLANS.md → 用户批准」高度同构；差异在于 Superpowers 把「回显 + 冲突前置」定为硬步骤，OmniDesk 现状靠自觉。

**建议：** GLM 规划会话吸收其三步节奏——(a) 动工前先读完任务涉及的代码与文档；(b) 第一轮回应先回显需求与风险，不直接跳到方案；(c) 存在悬而未决的关键分歧时，一次只问一个会改变方案的问题。

### 2. Writing Plans（计划制定）

**事实（关键条款）：**

- 计划写给「没见过这个代码库的工程师」：必须给出确切文件、确切名称与签名、确切的测试，计划没写明的留白由执行者做合理选择。
- 任务粒度标准：「一个任务 = 一个可独立测试的交付物 + 一个新评审者可独立把关的单元」。setup/脚手架/配置折进受益于它们的任务，不单列；只有"评审者可能批准 A 而否决 B"时才拆成两个任务。
- 每步是「一个动作 + 一个可检查结果」：写失败测试 → 跑确认失败 → 最小实现 → 跑确认通过 → 提交。
- 计划头强制字段：Goal / Architecture / Tech Stack / Spec 路径 / 全局约束（逐条一行）/ Review Focus。

**研究结论：** 这是对「规划任务过大、过于抽象」最直接的解药。OmniDesk 的 PLANS.md 已有类似字段（影响范围/风险/验收标准），缺的是「每任务自带验收测试与命令」的步进结构。

**建议：** GLM 拆任务时按此粒度产出任务卡；"失败测试→最小实现"的步进细节放到执行规范承接，计划里只写到「任务 + 验收命令」层，避免计划本身膨胀。

### 3. Executing Plans（执行控制）

**事实：** 内联执行模式的要点——「计划已完成思考，执行就是照做并逐步证明」；工具调用之间叙述不超过一行；遇到歧义由执行者裁决并记录 `Ruling: 决定 — 理由 — 错了代价`；只有四类事停下问人：不可逆/破坏性操作、安全敏感动作、工作区外的副作用（合并/推送/发布）、计划彻底坏到只剩猜。

**研究结论：** 四类停下条件与 OmniDesk「发现计划外差异即停止」条款同向，但更可操作（可枚举）。裁决留痕机制能减少 DeepSeek 的反复请示与重复分析。

**建议：** 直接吸收为执行规范的停下条件与裁决记录格式。

### 4. Subagent-Driven Development（子代理调度）

**事实：** 每任务派新子代理实施 + 任务级审查 + 收尾全分支审查；价值主张是上下文隔离——子代理不继承会话历史，指令自带全部所需上下文。

**研究结论：** OmniDesk 是两个独立会话（GLM 规划 / DeepSeek 实施），不是同一会话内的子代理，调度机制不适用（用户约束亦明确不引入）。但其"每任务新鲜上下文 + 任务级把关 + 最终审查"的质量结构可以映射到现有机制：DeepSeek 每任务新会话 + GLM 独立审查（REVIEW.md）。

**建议：** 不引入调度机制；只吸收「任务指令自带全部所需上下文」这一上下文构造原则，落到任务卡模板。

### 5. Test-Driven Development

**事实：** 铁律「没有先看到测试失败，就不写生产代码」；例外（原型/生成代码/配置）须问用户。

**研究结论：** OmniDesk 现状（从 STATUS.md / REVIEW.md 记录看）测试与实现同轮交付，验证脚本体系完整但"红灯先行"不固定。全程强制 TDD 与「不额外改变 DeepSeek 自主实施方式」的约束冲突。

**建议：** 放宽吸收——(a) 缺陷修复必须先用测试复现（Prove-It）；(b) 新行为任务在任务卡里写明验收测试；(c) 不要求实现前必须红灯，由 DeepSeek 在既定架构内自主安排。

### 6. Verification Before Completion

**事实：** 铁律「没有本轮新跑的验证证据，不得声称完成」；给出「声明→所需证据」对照表（声称测试通过须有 0 failures 的输出；声称修复须复跑原症状）；红旗词表（should / probably / seems to）。

**研究结论：** 与 AGENTS.md「STATUS.md 是执行记录不是验收证据、REVIEW 未通过不得标通过」完全一致，且比现行条款更可操作。

**建议：** 吸收为质量门禁验收条款：DeepSeek 报告只接受「本轮实跑命令 + 输出摘要（退出码/通过数）」，推测性措辞视为未验证。

### 7. Systematic Debugging

**事实：** 铁律「未完成根因调查不得提修复」；四阶段：根因调查（读错误原文、重现、读相关代码）→ 模式分析（可工作的对照）→ 假设验证 → 修复。

**研究结论：** OD-ARCH-135/136 的实际过程（已核实根因再实施）就是这个方法，但流程是隐性的、依赖实施者自觉。

**建议：** 显式写进执行规范的错误排查节；GLM 重新规划失败任务前，先检查 DeepSeek 报告是否完成了四阶段，缺哪段补哪段。

### 8. Git Worktrees

**事实：** 技能保证实施发生在隔离工作区；先检测既有隔离（含 submodule 误判防护），再建。

**研究结论：** OmniDesk 当前 main 单分支，工作区存在未提交改动（2026-11-04 实测：`desktop/src-tauri/src/lib.rs` 有未提交修改，HEAD `9414b34`）；AGENTS.md 要求保留全部既有改动、不得擅自提交推送；GOALS.md 记录过 OpenCode UI worktree 未合并的教训。双会话串行交接时，worktree 的隔离收益有限，而分支/合并流程与现有"不擅自提交"约束的交互复杂度不低。

**建议：** 暂缓。等出现「GLM 与 DeepSeek 真正并行修改同一仓库」的场景再评估；当前串行 + 获批文件范围保护足够。

## 三、对重点研究问题的回答

| 问题 | 回答 |
| --- | --- |
| 哪些机制适合 GLM 规划会话？ | Brainstorming 的回显与冲突前置；Writing Plans 的任务粒度与计划头字段；Verification 的声明→证据对照 |
| 如何把大功能拆成小任务？ | 一任务一独立可测交付物；评审者可单独把关才拆；脚手架折进受益任务 |
| 如何避免任务过大过抽象？ | 任务卡必须写确切文件、确切验收命令；写不出确切命令说明任务还没想清 |
| 每个任务应提供哪些信息？ | 获批依据、允许文件清单、明确不做、验收命令与预期、证据落盘路径、硬约束 |
| 如何设计任务依赖？ | 只标"阻塞/可并行"两级；依赖方向单向，出现互相依赖说明应合并为一个任务 |
| 如何让 DeepSeek 无需架构判断即可执行？ | 任务卡含架构契合说明（改哪个既有模块、沿用哪个模式）；歧义留给"裁决留痕"，只有四类事停下 |
| 如何减少重复分析与上下文消耗？ | 任务指令自带全部所需上下文（文件、行号、决策依据），执行者不从零扫描仓库 |

## 四、明确不引入的部分

1. 子代理调度（双会话模式不符 + 用户约束）。
2. Git worktree 隔离（暂缓，理由见上）。
3. 全程强制 TDD 红灯（放宽为缺陷复现先行 + 任务卡验收测试）。
4. 技能 announce 套话与全技能常驻（token 成本高；改由任务卡按需点名启用）。
