# OmniDesk 工程规范（草案，待用户批准）

> 状态：草案。依据：AGENTS.md 现行规则 + docs/development/SUPERPOWERS_ANALYSIS.md + ADDY_SKILLS_ANALYSIS.md + 2026-11-04 实测仓库状态（main / HEAD 9414b34 / lib.rs 有未提交改动）。
> 本文件获用户批准后生效；批准前现行流程不变。不修改源代码，本文件本身是文档。

## 0. 角色与分工（不变项）

- **GLM（规划会话）**：需求分析、方案确认、任务拆解、技术决策、依赖排序、验收标准、阶段交接、独立审查（REVIEW.md）。
- **DeepSeek（执行会话）**：按任务卡实施、测试、排错、报告。在任务卡边界内自主选择实现细节；架构判断不属于执行会话。
- 不派子代理；不改变双会话双模型分工。

## 1. 规划规范（GLM 执行）

### 1.1 需求分析与方案确认

1. 动工前读完任务涉及的代码与文档（对应代码行号），不问项目已回答的问题。
2. 首轮回应先回显：用户要什么、为什么、当前相关代码如何工作、本次改动会碰哪里。
3. 存在会改变方案的关键分歧时，一次只问一个最重要的问题；无分歧且只有一条合理路径时，直接给短设计请批准。
4. 大功能（捆绑多个可独立验收能力）先出能力地图：模块表（OD-ARCH 编号 | 职责 | 依赖）+ 构建顺序，经用户确认后逐模块展开计划。

### 1.2 任务拆解与任务卡

每任务一张任务卡，粒度标准：**一个任务 = 一个可独立测试的交付物，一次 DeepSeek 会话可完成，且 GLM 可单独批准或否决它而不牵连相邻任务**。脚手架、配置、文档更新折进受益于它们的任务，不单列。任务卡字段（沿用并精简现行 BUILDER 模板）：

    ## 任务编号与名称
    ## 获批依据        # PLANS.md 小节 + 批准时间 + 基线 HEAD
    ## 允许修改文件    # 逐项列出，超出即停
    ## 明确不做        # 相邻需求负面清单
    ## 架构契合        # 一行：改哪个既有模块、沿用哪个模式、为何不新增抽象
    ## 实施步骤        # 顺序步骤，每步一个可检查结果；不规定到代码写法
    ## 验收命令        # 确切命令 + 预期结果（通过数/退出码）
    ## 证据落盘        # tests/verification/... 路径
    ## 硬约束          # runtime/ 不动、凭证不碰、不提交推送
    ## 依赖            # 阻塞于哪些任务；与哪些任务可并行

写不出「验收命令」的任务说明还没想清，退回 1.1。

### 1.3 技术决策与依赖

- 决策记录进 docs/decisions.md（状态、理由、影响、证据、复审触发条件）；候选方案不得写成已决定。
- 依赖只标两级：阻塞 / 可并行。依赖方向单向；两个任务互相依赖时合并为一个任务。

### 1.4 审查（REVIEW.md）

五轴：正确性、可读性、架构、安全、性能。每轴查 diff 与实跑证据，不采信执行者自述。审批标准：明确改善整体代码健康度即通过，不求完美；不通过时写明问题、证据、严重程度、下一轮修复要求。重点核查三类降低门槛迹象：新增豁免（allow/ignore/unwrap 绕过）、跳过或删除既有测试、验收阈值被改低。

### 1.5 阶段交接

按 CONTEXT_MANAGEMENT_STANDARD.md 的交接文件格式生成交接文档；GLM 负责在交接前更新 GOALS/PLANS/STATUS/REVIEW 状态行。

## 2. 执行规范（DeepSeek 执行）

### 2.1 修改前检查

1. 记录 git status 与 HEAD，核对与任务卡基线一致；保留全部既有未提交/未跟踪改动。
2. 只读任务卡点名的文件与行号，不从零扫描仓库。
3. 核对允许修改清单；发现任务卡与代码现实冲突 → 停，写报告，不自行扩大范围。

### 2.2 实施边界

- 在任务卡边界内自主选择实现细节（函数结构、命名、内部写法）；不改任务卡未列的文件；不做任务未要求的重构、简化、依赖新增。
- 叙事纪律：工具调用之间叙述不超过一行；不输出与任务无关的分析、方案对比、日志摘抄。
- 裁决留痕：遇到任务卡未覆盖的歧义时自行决定并在报告记 `Ruling: 决定 — 理由 — 错了代价`，继续执行；只有四类事停下：不可逆/破坏性操作、安全敏感动作、影响工作区外状态（合并/推送/发布）、计划坏到只能猜。

### 2.3 测试验证

- 缺陷修复：先写复现测试证明缺陷存在（Prove-It），再修，再证明修复。
- 新行为：任务卡的验收测试为完成标准；测试命令用 §3.1 登记的仓库真实命令，不假设默认命令。
- 不为绿灯新增豁免、不跳过或删除既有测试、不改低阈值；报告须声明未新增豁免。

### 2.4 错误排查

停线规则：意外失败即停止推进，保留错误输出与重现步骤，按序走：复现 → 定位 → 最小化 → 根因 → 修复 → 防复发。未完成根因调查不得提修复方案；同一问题修复两次仍失败 → 停，出报告交回 GLM 重新规划。

### 2.5 实施报告（固定模板）

    ## 基线核对        # HEAD + git status 一行
    ## 改动文件        # 与任务卡允许清单逐项对照
    ## 实跑命令与结果  # 命令 + 退出码 + 通过数，只接受本轮新跑
    ## 裁决记录        # Ruling 条目（无则写"无"）
    ## 未做与已知限制
    ## 豁免声明        # 未新增 allow/ignore/跳过测试/改低阈值
    ## 计划偏差        # 与任务卡不一致处（无则写"无"）

推测性措辞（"应该通过"/"大概率没问题"）视为未验证。STATUS.md 是执行记录；验收结论只由 GLM 的 REVIEW.md 给出。

## 3. 质量门禁（按任务类型分级，不要求每任务全跑）

### 3.1 仓库验证命令清单（一次登记，所有会话引用）

| 用途 | 命令 | 来源 |
| --- | --- | --- |
| 宿主单测 | `cargo test --offline --lib` | STATUS.md OD-ARCH-136 实跑记录 |
| 前端构建 | `npm --prefix desktop run build` | 同上 |
| Python 测试 | `pytest` | docs/decisions.md D-060 证据 |
| 专项验证 | `python3 tests/verification/desktop/verify_*.py` | 各任务卡指定 |
| 集成/回归 | cargo `--tests` 分组 | D-060 证据 |

执行会话不得自行发明命令；发现清单缺失或过时 → 报告 GLM 更新本表。

### 3.2 门禁分级

| 任务类型 | 必跑 | 按需 |
| --- | --- | --- |
| Rust 逻辑/命令改动 | cargo lib 单测 + 任务专项 verify 脚本 | cargo --tests、pytest（触及共享层时） |
| 前端 UI 改动 | tsc + vite build（build 已含 tsc --noEmit）+ 任务专项 verify | 相关 Rust 单测（触及 IPC 层时） |
| 缺陷修复 | 复现测试 + 任务专项 verify + 受影响模块单测 | 全量 lib 单测（改动跨模块时） |
| 打包/发布改动 | 对应 verify_*.py + 本机构建核对产物结构 | CI 出包核对 |
| 纯文档 | 无 | — |

安全检查适用条件：触及凭证/数据落盘/网络端点/文件写出的任务必查（数据政策合规 + 无真实材料入测试夹具/日志）；架构边界检查：任务卡「架构契合」行由 GLM 在审查时核对（runtime/ 零改动为红线）。Git 变更审查：每任务报告后 GLM 核对 diff 与允许清单。
