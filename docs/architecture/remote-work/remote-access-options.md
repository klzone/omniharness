# 中央 Agent 远程访问方案比选（Step 8）

- 日期：2026-11-27
- 比较对象：① 私有网络/VPN + OmniDesk Web；② SSH 隧道 + OmniDesk Web；③ 受控远程访问网关。

## 1. 方案对比

| 维度 | A. Tailscale 私网 + Web | B. SSH 隧道 + Web | C. 受控网关（自建/frp/Cloudflare Tunnel） |
| --- | --- | --- | --- |
| 安全 | WireGuard 加密，设备级准入，回环之上仍可加 token；无公网暴露 | 加密；密钥管理靠用户；端口不暴露 | 取决于实现；自建网关是最大攻击面，需自己维护 TLS/认证/限流 |
| 部署复杂度 | 低：两端装 Tailscale，tailnet 内直连 | 低：ssh -L 转发即可 | 高：网关进程/域名/证书/更新 |
| 稳定性 | 好：NAT 打洞，设备在线即达；离线自动失效 | 差：隧道随终端会话断，需保活脚本；换网络重连 | 中：依赖云侧可用性 |
| 移动端体验 | 好：iOS/Android 客户端成熟，系统级 VPN，浏览器直接访问 | 差：移动端维持隧道不现实 | 中：需域名+HTTPS 才能浏览器用 |
| 维护成本 | 极低：服务本身免维护 | 低但体验差：每次手动开隧道 | 高：网关是长期运维负担 |
| 多终端并发 | 好：多设备同时在线各自动连 | 差：一条隧道一个转发 | 好 |
| 离线/换网适应 | 好（tailnet 常在） | 差 | 中 |

## 2. 结论（唯一主方案）

**方案 A：Tailscale 组网 + 中央 Host 暴露认证 API/Web。**

理由：

1. 用户场景（办公室/家/移动多终端、手机平板访问）要求"网络常在"，SSH 隧道做不到；网关复杂度与单用户规模不匹配。
2. Tailscale 不替代 OmniDesk 认证，只解决"网络可达 + 链路加密"；API 层仍加认证令牌（与现有 token 交换模式一致）。
3. B 作为临时调试手段保留（不需要实现），C 不采用。

## 3. 每项技术选型回答（Step 8 涉及项）

| 技术 | 为什么需要 | 现有架构能否实现 | 更简单替代 | 额外成本 | 实施阶段 | 必要性 |
| --- | --- | --- | --- | --- | --- | --- |
| Tailscale | 多终端跨网私连，免公网暴露 | 现有全回环，无法远程 | SSH 隧道（体验差） | 低（第三方服务，免费档够用） | Phase 1 | 必须 |
| API 认证令牌 | 防止 tailnet 内未授权操作 | 无，需新增 | 无（不能裸奔） | 低 | Phase 1 | 必须 |
| Web UI | 手机/平板无 Tauri 客户端 | 无，需新增 | RDP/屏幕共享（移动端不可用） | 中：React 复用 + HTTP 化命令 | Phase 1（最小）、Phase 2（完善） | 必须 |
| WebSocket/SSE | 任务事件实时推送 | Engine 推拉事件已具备，缺 HTTP 转发 | 轮询（简单但体验差） | 低 | Phase 1 最小可用轮询，Phase 2 加 WS | 非首期必须 |
| 文件传输 API | 成果/附件跨端读写 | 宿主文件能力已有，缺 HTTP 面 | Syncthing（破坏单写者） | 低 | Phase 2 | 必须 |
