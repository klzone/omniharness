# OmniDesk 价值评测协议（草案 v0.1）

> 状态：**草案**，随「阶段 2.5 项目准入与价值评测基线」生效
> 上位文档：[GOALS.md](../GOALS.md)、[docs/decisions.md](decisions.md)、[知识入库与脱敏规则](OmniDesk-Knowledge-Ingestion-and-Desensitization-Policy.md)。协议仍是评估方法材料，不代表已经取得真实业务授权或基线结果。
> 制定日期：2026-10-16
> 一句话原则：**先定规则，再跑评测；未获书面授权，只测技术与流程表现，不宣称真实业务收益。**

---

## 一、目的与边界

本协议回答一个问题：**OmniDesk 到底值不值得产品化？**

它把「效率提升」「质量可靠」「合规安全」从主观印象变成**可复现、可复核**的度量。

**明确不做**：

- 不把免费 GPT 的回答、文档里的设计承诺或历史报告中的数字当作评测证据；
- 不在未取得书面授权时使用真实工作材料；
- 不用未验证的工作流（如会议整理）凑评测数量。

**证据等级**（与全项目一致）：`static`（文件/源码事实） · `script`（脚本或进程运行） · `model`（真实模型输出） · `unverified`（未验证）。
每条结论必须标等级；未实际运行的项标 `unverified`。

## 二、评测前置条件（先满足，再开始）

| 条件 | 要求 | 未满足时 |
| --- | --- | --- |
| 数据准入 | 评测素材属**合成 / 公开 / 已书面批准**之一 | 只用合成与公开素材，结论仅限技术与流程 |
| 能力范围 | 只评**材料写作**与**知识检索** | 其他能力标「未验证」，不计入 |
| 运行隔离 | 使用 OmniDesk 隔离实例，不触碰原版 `~/.dsh`、`~/.agents` | 停止评测 |
| 凭证与路由 | 使用隔离实例自身凭证；**不更改**凭证、模型路由或用户数据 | 记录阻塞，不私自换路由 |
| 记录可复现 | 保存输入、输出、事件与判定；判定脚本可确定性复现 | 该次评测不计分 |

## 三、任务分层与选择

评测任务按**难度与风险**分三层，每层按**预定义规则**抽取，不允许事后挑样本。

| 层级 | 说明 | 建议配额 | 选择规则 |
| --- | --- | --- | --- |
| **L1 基础确定性任务** | 结构明确、有模板可依、事实齐备（如给定数据的总结） | ≥ 40% | 从 `tests/golden_tasks/tasks.json` 中按类别固定抽样，样本一次抽定后封存 |
| **L2 决策与边界任务** | 数据缺失、事实冲突、无适配模板、需按用途自拟结构 | ≥ 40% | 覆盖「待确认标注」「冲突指出」「无模板按用途组织」三类，各层至少 1 例 |
| **L3 可靠性压力任务** | 长文、多轮修改、跨文件检索、引用密集 | ≤ 20% | 用于观察返工与引用稳定性；不用于制造高分 |

**分层选择纪律**：

1. 抽样规则、样本清单与随机种子在评测**开始前**写入 `tests/verification/value-eval/`，评测中不得改动；
2. 每层至少 5 个任务，总量建议 ≥ 20；样本总量不足时如实标注覆盖率，不虚报；
3. 禁止用同一任务重复计分（返工与重试单独记入返工列，见 §6）。

## 四、耗时度量（口径必须一致）

效率提升 = 净节省，而不是「AI 生成快」。

### 4.1 人工基准工时（人工基线）

对每个任务，先由人工**照常完成**一遍，记录纯工作时间：

- **人工基准工时** = 从动手到成稿的实际投入时间，**不含**通勤、开会等无关时间；
- 同一任务若有历史人工耗时记录，优先采用并注明来源；
- 基线必须由**同一人**在**同口径**下完成，不同口径的快照不可混算。

### 4.2 AI 辅助总工时（关键：不是「生成耗时」）

AI 辅助总工时**必须包含全过程**，只记生成耗时会系统性夸大收益：

| 计入项 | 说明 |
| --- | --- |
| 准备 | 素材整理、模板选择、规则阅读、任务描述撰写 |
| 等待 | 模型排队与运行时间（含长任务） |
| 核验 | 逐条核对事实、引用、条文与来源位置 |
| 返工 | 因质量或方向不符而重做的轮次（含人工重写） |
| 修正 | 定稿前的润色、事实更正、格式调整 |

**净节省率** = (人工基准工时 − AI 辅助总工时) ÷ 人工基准工时 × 100%。

> 未计入准备、等待、核验、返工与修正的耗时数据**视为无效**，不得用于门槛判定。

## 五、质量与合规硬门槛（一票否决）

任何一项硬门槛不达标，该批次评测判为**不通过**，不进入净节省率判定。

### 5.1 合规硬门槛（否决项）

1. 是否处理了案件材料、案件线索、未公开调查信息等**三级敏感数据**——一旦发生，**直接否决**，且立即停止；
2. 是否在**未获书面授权**的情况下接入真实工作材料或内部文件——一旦发生，**直接否决**；
3. 是否以「自动脱敏」为由绕过红线——一旦发生，**直接否决**。

### 5.2 质量硬门槛

| 指标 | 要求 |
| --- | --- |
| 引用真实性（知识检索） | 文件、原文、条款位置**逐字可核验**；编造出处 **0 容忍** |
| 引用准确率 | ≥ 95%（与设计原则 §9 的 ≥ 90% 取更严者） |
| 无证据时的行为 | 明确说明未检索到足够依据，**不以常识补成制度结论** |
| 事实与判断分离 | 文稿中事实、分析、判断、建议可区分 |
| 数据真实性 | 未虚构数据、政策依据、文件名称、文号、工作成效或领导要求 |

## 六、失败与遗漏记录

评测必须如实记录**没成功**的项，否则数字没有意义。每次任务记录：

- **失败类型**：拒绝执行 / 输出不可用 / 引用错误 / 结构错误 / 超时 / 阻塞；
- **遗漏**：应当覆盖但未覆盖的场景、未验证能力、样本缺口；
- **人工介入点**：在哪一步由人纠正了方向或事实，纠正了几次；
- **返工轮次**：每轮的原因与耗时；
- **终止原因**：取消、超时、引擎不可用等，标 `unverified` 而非通过。

**判定护栏**：静态检查、脚本自检与真实模型输出**分别记录**；不得用静态检查结果冒充运行测试通过，也不得根据 Prompt 内容推断模型一定遵守。

## 七、成本维度

| 成本 | 记录方式 |
| --- | --- |
| 模型成本 | 每个任务的调用次数、token 用量与费用（若可得）；不可得时标注缺失，不估算成结论 |
| 等待成本 | 已计入 AI 辅助总工时的「等待」项 |
| 维护成本 | 每次底座升级、Skill 调整、资产同步所花费的人工时间单独记账 |
| 资产沉淀 | 新增/复用的模板、风格规则与范例数量（衡量是否形成个人资产） |

成本不达标（如维护成本长期超过节省）本身可以构成「不产品化」的结论。

## 八、评分规则与复现条件（预先定义）

### 8.1 预定义评分

在评测**开始前**冻结：

- 每个任务的**通过/不通过**判据（可脚本化的自动判定 + 人工复核规则）；
- 每层权重与总分计算方式；
- 硬门槛清单（§5）与一票否决规则；
- 净节省率的计算口径（§4）。

评测中**不得**修改判据；若必须调整，须作废当前批次并重新冻结。

### 8.2 复现条件

一次评测可复现，需同时满足：

1. 输入素材与任务清单版本固定（记录 Git 提交或文件哈希）；
2. 模型与服务商、参数（如 reasoning effort）明确记录；
3. 隔离环境与底座版本（DSH tag + commit）明确记录；
4. 判定脚本可离线重跑（如知识检索的 `--rejudge`，不调用模型即得同结果）；
5. 原始输出与事件证据留存于 `tests/verification/value-eval/evidence/`。

缺少任一项，该批次结论标为**不可复现**。

## 九、产品化判定（与路线图阶段 2.5 联动）

本协议产出的结果，用于判断路线图「阶段 2.5.4 产品化联合决策门槛」是否满足：

1. 可复现的**净节省率 > 20%**；
2. 质量与合规**硬门槛达标**；
3. 至少一位同事愿意在**获准条件**下实际试用；
4. 存在**由桌面应用能解决**的具体痛点。

四项全满足，才评估 Tauri / Electron 等产品形态；**满足门槛不等于自动启动开发**，仍需用户明确批准。
未满足时，结论应如实写为「当前证据不足以产品化」，并列出缺口，而不是降低门槛。
