## 一、使用说明

**执行状态**：`未执行` / `已执行-通过` / `已执行-未通过` / `已执行-部分`。本矩阵当前状态：E01–E17、E19、E20 为 `已执行-通过`；E18 为 `已执行-部分`。

**证据类型**：

- `static` —— 文件事实 / 静态检查
- `script` —— 脚本或隔离进程实测
- `model` —— 真实模型输出
- `unverified` —— 尚未验证

**执行环境前提（全部场景）**：

1. 使用**一次性临时数据根**（启动级环境变量 `DSH_HOME` / `DSH_AGENTS_HOME` 指向 `/tmp` 下的独立目录），绝不指向 `~/.dsh`、`~/.agents`、`~/OmniDesk`、`~/YvanAI`。
2. 全部输入为**纯合成虚构素材**，不含真实人员、机构、案件或内部信息。
3. 不读取、不打印、不复制任何凭证。
4. 对比基准：测试前后对上述四个目标目录做元数据快照，差异须全为 0。

## 三、场景明细

### E01 正常提交

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - 测试引擎进程可用，隔离数据根已创建。
  - 提交一份合成写作任务（虚构素材）。
- 操作步骤：
  - 合成输入：虚构的年度工作总结要点（无真实单位/人员）。
  - 操作：`submit_task` 提交，保存返回的 `omni_task_id` 与初始状态。
- 预期状态与事件：状态进入 `queued` 或 `starting`；返回稳定 `omni_task_id`；若底层返回 `engine_session_id`，仅记入适配层。
- 可复核证据：
  - 返回收据 JSON（`omni_task_id` / `status` / `accepted_at`）。
  - 进程日志（脱敏）。
- 通过标准：`omni_task_id` 为稳定标识且与 `engine_session_id` 不同层；受理状态明确；未重复执行。
- 未支持能力的处理方式：若通道不接受该提交，须返回标准错误（如 `engine_unavailable`），不得伪造受理。

### E02 流式输出

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - E01 已受理同一任务。
- 操作步骤：
  - 重复使用 E01 的合成输入。
  - 操作：`stream_events` 订阅，记录全部事件与 `seq`。
- 预期状态与事件：收到 `task_started`、若干 `text_delta`/`progress`，最终 `text_delta` 拼接与 `get_task_result` 完整结果一致。
- 可复核证据：
  - 事件序列 JSONL（含 `seq`/`occurred_at`）。
  - 最终完整结果原文。
  - 两者一致性比对脚本输出。
- 通过标准：增量拼接结果与最终完整结果**一致**；增量与最终结果分离存储。
- 未支持能力的处理方式：若底层无 token 级流，须标注为归一化/有界投影，不得声称 token 级流式。

### E03 正常完成

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - E01 任务已执行。
- 操作步骤：
  - 同上合成输入。
- 预期状态与事件：状态经 `running` -> `succeeded`；`get_task_result` 返回 `form=complete`。
- 可复核证据：
  - `get_task_status` 快照序列。
  - `TaskResult`（含 `persisted_at`、`integrity=complete`）。
- 通过标准：终态为 `succeeded` 且完整结果可取回；未把进程退出直接当作成功（须有结果证据）。
- 未支持能力的处理方式：若通道不能区分成功/失败（如 headless），须标注降级并说明判定依据。

### E04 执行失败

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - 构造必然失败的合成条件（如故意无效的受控参数，或底层返回错误）。
- 操作步骤：
  - 合成输入 + 会触发失败的条件。
- 预期状态与事件：状态进入 `failed`；`TaskResult.form=partial` 或明确错误；错误结构符合契约 4.9。
- 可复核证据：
  - 错误对象（`code`/`message`/五属性）。
  - 失败前已接收的部分输出。
- 通过标准：失败被明确报告；错误结构完整；已接收输出保留且标注非完整。
- 未支持能力的处理方式：失败必须以标准错误暴露，不得把底层 `-32603` 直接抛给 UI。

### E05 用户取消

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - E01 任务处于 `running`。
- 操作步骤：
  - 合成输入 + 在运行中发出取消。
- 预期状态与事件：任务在取消期间进入 `cancelling`；`cancel_task` 返回 `request_sent` 或 `acknowledged`；收到可靠终态证据后才转 `cancelled`（含 `confirmed_cancelled`）。
- 可复核证据：
  - `CancelOutcome` 序列。
  - 引擎终态事件。
  - 状态机转换日志。
- 通过标准：严格区分「请求已发送」与「确认终止」；仅在可靠证据下报告取消完成。
- 未支持能力的处理方式：headless/sdk 无取消：须返回 `unsupported`，并以 `process_terminated` 记录，不得谎报优雅取消。

### E06 取消与完成竞争

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - 任务接近完成时发出取消。
- 操作步骤：
  - 合成输入 + 临界时序取消。
- 预期状态与事件：终态唯一：要么 `succeeded` 要么 `cancelled`，不得同时出现或互相覆盖。
- 可复核证据：
  - 状态机最终快照。
  - 双方事件时序记录。
- 通过标准：不产生互相矛盾的终态；按契约 3.3 的仲裁优先级判定（引擎终态证据优先）。
- 未支持能力的处理方式：若先得成功终态，则不得改判为 `cancelled`；须记录该情形。

### E07 客户端强制退出

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - 任务运行中，强制终止适配层/客户端进程（SIGKILL）。
  - 保留隔离数据根以观察重启行为。
- 操作步骤：
  - 重启适配层（新进程，同一隔离数据根）。
  - 查询该 `omni_task_id` 状态。
- 预期状态与事件：能识别真实任务状态：`interrupted` 或 `unknown`（依据底层是否留下终止记录）；不得报成功。
- 可复核证据：
  - 重启前后进程日志。
  - `get_task_status` 结果。
  - 引擎侧会话列表。
- 通过标准：重启后能识别真实状态；无法确认时进入 `unknown`/`interrupted`；**不自动重放**。
- 未支持能力的处理方式：若底层无终止记录（第一步审计中 ACP 被强杀即为该情形），须如实标注 `unknown`。

### E08 会话恢复

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - 存在一个既有 `engine_session_id`（来自先前任务）。
- 操作步骤：
  - 按 `engine_session_id` 调用 `recover_session`。
- 预期状态与事件：恢复该既有会话，**不隐式新建**；`recover_task` 单独恢复任务状态/事件/已有结果。
- 可复核证据：
  - `SessionRecovery` / `TaskRecovery` 结果。
  - 引擎侧会话 ID 比对（须为同一会话）。
- 通过标准：恢复的是既有会话；未新建；恢复不触发自动重放。
- 未支持能力的处理方式：若引擎拒绝恢复，须返回 `recover_failed`，不得静默新建会话。

### E09 未知会话

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - 使用一个不存在的会话 ID。
- 操作步骤：
  - 以伪造/未知 `engine_session_id` 调用恢复。
- 预期状态与事件：返回明确的 `unknown_session`（底层应为 `-32602 session is not resumable` 一类），**不创建新会话**。
- 可复核证据：
  - 错误对象。
  - 引擎侧会话列表（数量不变）。
- 通过标准：明确报错，不新建会话；错误映射为标准码，不泄露底层码。
- 未支持能力的处理方式：SDK 通道惰性创建未知会话，必须显式限制用途，不得当作恢复成功。

### E10 中断任务

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - 任务处于运行中，发生进程中断（同 E07）。
- 操作步骤：
  - 重启后查询中断任务。
- 预期状态与事件：状态为 `interrupted` 或 `unknown`；不自动重放；不伪造结果。
- 可复核证据：
  - 状态快照。
  - 是否存在自动重放的日志证据（须为否）。
- 通过标准：不自动重放；不伪造结果；明确标注非完整。
- 未支持能力的处理方式：若无法确认执行结果，进入 `unknown`；须在契约中标注底层限制。

### E11 事件断流

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - 流式订阅过程中，制造一次连接中断（如关掉读取端后重连）。
- 操作步骤：
  - 订阅中途断开并重连同一任务。
- 预期状态与事件：断流可被识别（`seq` 缺口）；重连后保留已收到的部分输出，不重复也不遗漏（在底层允许范围内）。
- 可复核证据：
  - 事件序列的 `seq` 缺口记录。
  - 部分输出快照。
- 通过标准：断流可识别；已收到部分输出被保留；未合成缺失事件为成功。
- 未支持能力的处理方式：若底层不提供重放，须标注断流区间并标记 `integrity=partial`。

### E12 重复事件

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - 人为注入重复/乱序事件（在适配层测试桩内，不改 runtime）。
- 操作步骤：
  - 喂入重复与乱序事件序列。
- 预期状态与事件：按 `seq` 去重与重排；结果不被重复拼接；任务不被重复执行。
- 可复核证据：
  - 归一化后的事件序列。
  - 结果内容比对（无重复片段）。
- 通过标准：不重复拼接结果；不重复执行任务。
- 未支持能力的处理方式：若底层无 `seq`，适配层须自行生成单调序号，并标注推导规则。

### E13 最终结果未落盘

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - 引擎已完成，人为使本地持久化失败（如指向只读/满盘临时路径）。
- 操作步骤：
  - 在持久化会失败的条件下完成一次任务。
- 预期状态与事件：能区分「引擎完成」与「本地持久化完成」；状态不因本地失败而虚报成功；返回 `result_persist_failed`。
- 可复核证据：
  - 引擎完成事件。
  - 本地持久化错误。
  - 最终状态。
- 通过标准：区分引擎完成与落盘完成；本地失败被明确报告；不丢失已接收内容。
- 未支持能力的处理方式：不得因本地持久化失败而重跑任务来伪造已保存。

### E14 优雅关闭

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - 存在在途任务或无在途任务的两种情形。
- 操作步骤：
  - 调用 `shutdown(graceful, grace_period)`。
- 预期状态与事件：分别处理三类操作（关闭连接 / 停止本地进程 / 取消远端任务）；返回 `ShutdownReport`。
- 可复核证据：
  - `ShutdownReport`。
  - 关闭时在途事件与落盘状态。
- 通过标准：关闭行为符合契约 4.8；在途结果按策略落盘或明确标记未落盘。
- 未支持能力的处理方式：若通道无显式关闭（headless），须记录为进程结束语义，不声称优雅关闭。

### E15 关闭超时

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - 存在无法在宽限期内结束的任务。
- 操作步骤：
  - 在任务不接受取消的条件下触发关闭。
- 预期状态与事件：超时后被记录为「仍运行」或「状态未知」；强制终止的后果被记录。
- 可复核证据：
  - 关闭超时日志。
  - 强制终止后状态。
- 通过标准：明确记录仍运行或状态未知；未把强制终止当作正常关闭。
- 未支持能力的处理方式：下次启动须按恢复策略处理，不自动重放。

### E16 引擎不可用

- 目标通道：`acp`
- **当前是否已执行**：**已执行-通过**
- 前置条件：

- 操作步骤：

- 可复核证据：
  - 错误对象。
  - 不存在的任务不会被创建的证据。
- 通过标准：失败可诊断；不假报任务成功。
- 未支持能力的处理方式：不得静默回退到语义不同的通道。

### E17 不支持的能力

- 目标通道：`headless / sdk`
- **当前是否已执行**：**已执行-通过**
- 前置条件：
  - 分别以 headless 与 sdk 通道运行同一契约测试。
- 操作步骤：
  - 在 headless 上调用 `cancel_task`；在 sdk 上调用 `cancel_task` / `recover_session`。
- 预期状态与事件：两项均返回明确的 `unsupported`；不进行语义不等价的降级。
- 可复核证据：
  - 各通道返回的 `unsupported` 错误。
  - 能力矩阵标记。
- 通过标准：返回明确 `unsupported`；无隐藏降级。
- 未支持能力的处理方式：以第一步审计为设计依据：headless 无取消旗标；sdk 实测 `session/cancel` 与 `session/resume` 均为 `-32603 unknown method`。**本场景已于本轮重跑复现**（证据 `E17.json`）。

### E18 任务用途配置

- 目标通道：`acp`
- **当前是否已执行**：**已执行-部分** —— script 臂（配置覆盖进入模型请求）**通过**；model 臂（真实模型人格前缀对照）**阻塞**（进程环境无任何 API 密钥环境变量，隔离根凭证文件按硬约束未读取）
- 前置条件：
  - 准备两组配置：默认 personaPrefix 与覆盖后的 personaPrefix；其余配置指纹一致。
- 操作步骤：
  - 同一合成非编码任务（P-A/P-B/P-C），两组配置各跑一次。
  - 用离线 `--dump-config` 记录实际生效 personaPrefix。
