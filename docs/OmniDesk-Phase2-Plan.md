## 0. 结论摘要

1. Web config 页面并不指向旧版 DSH。它显示的是当前实例的组合配置，其中"看起来像默认值"的部分来自 dsh-base Bundle 的静态默认层，而真正生效的模型（agnescom / agnes-3.0-flash）来自 yvan-work Profile 补丁层。隔离没有被破坏。[源码 + 实测]

2. Web 页面在设计上不会、也无法显示配置文件的物理路径。配置契约里根本没有 path 字段，路径信息只存在于主机侧（写入目标为当前 Profile 的 patch 文件）。因此"在页面上看不到独立数据目录"是预期行为，不构成隔离失败的证据。[源码]

3. 真正的阻断问题在材料写作 Skill 这一侧：Skill 的发现链路已经接通，但 Skill 内部引用的三类本地资产（模板库、风格库、历史范例）路径无法在运行时解析，文件读取链路是断的。[源码 + 实测]

4. 三个参考源中，历史优秀范例目录当前只有说明文件，没有实质内容，属于"声明存在但实际为空"。[实测]

5. 本阶段的验收任务定为一个匿名的半年工作总结起草任务，采用人工评分表，硬门槛与评分项分离，并预埋三处缺陷用于检验 Skill 是否会追问而不是编造。

6. 修复方案以"最小改动 + 官方机制优先"为原则，共 7 步，其中第 1、2、3 步是阻断项。不新增 Agent、Core 层、Registry 或自研 GUI。

## 1. Web config 问题的诊断结论及证据

### 1.1 证据分级

本报告严格区分三类证据，后文每条结论都带标签：

| 标签 | 含义 |
| --- | --- |
| [源码] | 在当前检出的 DSH 源码或仓库文件中直接读到的事实，可复核 |
| [实测] | 在本机以只读命令实际观察到的现象（进程参数、监听端口、配置导出、文件比对） |
| [推断] | 尚未被源码或运行验证证实的解释，需要后续步骤确认 |

### 1.2 子问题逐条回答

#### Q1 当前 Web 页面展示的 config 究竟是什么配置？

结论：它是**运行时组合后的有效配置 + Bundle 继承基线 + 当前用户覆盖值**三者并列展示，既不等于磁盘上的某一个文件，也不等于运行时数据根。[源码]

依据：

- settings 服务的 describe 返回结构为每条配置项给出 value / base / user 三个投影字段。[源码] 其中 value 取自当前已合并生效的配置，base 取自继承链上的 Bundle 默认层，user 取自当前 Profile 的覆盖值。三者都经过同一套表单投影，输出的是表单字段，不是原始文件内容。
- 该契约中不存在任何表示"配置文件路径"或"数据根"的字段。[源码] 也就是说，UI 即使想显示路径也没有数据来源。
- 数据根一类的路径信息在源码中只以符号标签形式存在（例如波浪号形式与美元变量形式的环境变量名），且其唯一消费方是 agent 指令文件模块，不属于 Web 设置页。[源码]

因此，下方 Q5 中"页面看起来像旧版 DSH"的现象，来源是 base 层，而不是配置被改写或回退。

#### Q2 当前 Web 服务对应哪个进程、CLI 入口、启动参数和 Profile？

结论：存在**多个并行实例**，全部绑定回环地址、全部使用隔离数据根、全部运行 yvan-work Profile；另有一个与本任务无关的原版 Desktop 实例在运行。[实测]

依据（ps 与监听端口只读观察）：

| 实例 | 进程 | 数据根 | 端口 |
| --- | --- | --- | --- |
| OmniDesk 主实例 | PID 59932 | 家目录下 OmniDesk/runtime/dsh-home | 3210 |
| 复现实例 | PID 69851 | 临时目录 omnidesk-repro | 3300 |
| 陈旧复现实例 | PID 109609 | 临时目录 omnidesk-stale-repro | 动态分配（42415，另有 inspector 9232） |
| 原版 Desktop | Electron 主进程 144862 / host 145373 | 原版数据根（未设置隔离变量） | 37975（另有 9233） |

- 三个隔离实例的 CLI 入口完全一致：以打包的 Electron 二进制作为 Node 运行 asar 内的 DSH CLI，参数为 --profile yvan-work --host 127.0.0.1 --no-open，工作目录均为仓库根。[实测]
- 该入口形式恰好说明 Web 服务来自隔离实例，而非原版 Desktop。[源码 + 实测]

#### Q3 实际生效的 DSH_HOME、DSH_AGENTS_HOME 是什么？是否位于 OmniDesk 独立目录？

结论：两个变量在三个隔离实例中都被显式重定向到各自的隔离根，均不在原版数据根之下。[实测]

依据：

- 进程环境显示 DSH_HOME 与 DSH_AGENTS_HOME 分别指向各实例自己的 runtime/dsh-home 与 runtime/agents-home。[实测]
- 启动器在启动前对这两个解析结果做硬性校验：必须位于 OmniDesk 根之下，必须不落入原版数据根，两者不得相同，Profile 实际路径必须落在隔离根内且不能是软链接。[源码]
- 原版 Desktop 实例的环境中没有设置这两个隔离变量，两套环境互不覆盖。[实测]

需要说明的边界：确认隔离成立，依赖的是"进程环境 + 源码解析规则"，而不是 Web 页面上的任何字段。

#### Q4 yvan-work 实际从哪里加载？Bundle、Profile 补丁、模型配置、Skills 分别从哪读？

结论：Profile 从隔离根下的 profiles/yvan-work 目录加载，其内容由仓库模板 profiles/yvan-work 在首次启动时复制而来；Bundle 清单、补丁层、模型配置都来自该目录内的两个文件；Skills 走 DSH 默认的发现根，而不是仓库的 skills 目录。[源码 + 实测]

依据：

- 启动器在隔离根内不存在该 Profile 时，才从仓库模板复制 package.json 与 cordis.patch.yml。[源码] 当前隔离根内已有副本，且该副本与仓库内的 material-writing 技能文件逐字节一致。[实测]
- 模型配置写在 Profile 补丁层的 llm-pi-ai 与 agent-default-model 两条补丁里：默认模型为 agnescom / agnes-3.0-flash，思考档位 high。[源码 + 实测]
- Skill 发现根由 skill-filesystem 插件按优先级排列：项目级目录、自定义目录、用户级目录、随包目录。仓库根下的 skills 目录**不在**这个集合中。[源码]

这一条是第 2 节全部问题的根源，详见 2.1。

#### Q5 页面显示的配置与实际生效配置是否一致？

结论：**一致，但呈现层次不同**，容易误读。页面上的默认值来自 base 层，实际生效值来自 Profile 补丁层，二者都真实存在于配置树中，只是分属不同层。[源码 + 实测]

依据：

- base Bundle 的静态默认把默认模型设为官方 provider 与 flash 模型。[源码]
- yvan-work 补丁层把默认模型覆盖为 agnescom / agnes-3.0-flash，并覆盖 thinking 档位。[源码]
- 在一次性临时根中执行配置导出，输出中明确出现补丁层来自 profiles/yvan-work/cordis.patch.yml 的行，其后是被覆盖后的模型条目与 provider 条目。[实测] 这直接证明补丁层被应用，而非被忽略。
- base 层模型条目同时出现在导出结果中，说明它在组合树里依然存在，只是被上层覆盖。[实测]

所以这是显示层次问题，不是配置来源问题，也不是隔离失效。

另有一处需要区别对待的现象：设置页上的用户偏好写入目标取决于页面是否运行在本机回环地址。当页面不是通过回环地址访问时，偏好写入会被短路而不落盘。[源码] 我们的实例绑定 127.0.0.1，因此该分支不适用。若日后通过网络地址访问，会出现"改了设置不生效"的现象，届时不要误判为隔离问题。

#### Q6 是否存在配置回退、默认 Profile 覆盖、旧端口混淆或浏览器访问了其他实例？

结论：**存在两种真实的混淆来源，都不是配置回退**。

（a）端口混淆。[实测]

- 3080 端口当前没有任何监听者。[实测] 该端口早前是一个社区界面残留标签页的地址，相关排查已记录在既有文档中。[实测] 若浏览器仍停留在该标签页，看到的是与当前实例无关的旧页面。

（b）设置页呈现不完整。[源码 + 实测]

- 设置页的通用命名空间在同一个进程内会间歇性地不出现在 describe 结果里，属于官方时机问题。[实测]
- 该命名空间的语义是诊断视图、预设选择、变更摘要与脚本化 HTML 预览等，本项目的补丁层已将整个 ui-settings 条目禁用。[源码] 这一禁用的作用范围尚需一次运行确认。[推断]

需要明确排除的三项：

- 没有发现任何"默认 Profile 覆盖用户 Profile"的机制在起作用：Profile 名由启动器固定，且启动器拒绝透传覆盖 Profile 或补丁来源的参数。[源码]
- 没有发现配置被回退到磁盘默认值的痕迹。[实测]
- 没有证据表明浏览器访问到了原版 Desktop 实例：两者监听端口不同，且隔离实例的数据根与原版数据根无交集。[实测]

### 1.3 为什么会产生"配置仍指向旧版 DSH"的印象

三条同时成立的原因，共同造成这一印象：

1. 设置页并列展示 base 层与生效层，base 层的官方默认值对用户是可见的。[源码]
2. 设置页被设计为不展示任何路径信息，用户无法从页面上确认实例使用的是哪个数据根。[源码]
3. 浏览器中存在指向旧端口的历史标签页。[实测]

判断实例实际使用哪个数据根，可靠的方法是读取启动器打印的隔离根路径，而不是阅读 Web 设置页。

### 1.4 本节结论

Web config 没有指向旧版 DSH，隔离完好。本阶段**不需要**为此改动 Runtime 或脚本逻辑，只需补齐说明性文字（见第 5 节 Step 7 的可选项）。Phase 2 的实际工作重心应当放在第 2 节的 Skill 链路上。

### 2.2 逐条回答（对应任务书第 2 节）

#### （1）Skill 是否被当前 yvan-work Profile 实际发现和加载？

结论：**能发现，但发现的是隔离根内的副本，不是仓库里的源文件。**[源码 + 实测]

- 技能发现按优先级取用目录，仓库根的 skills 目录不在发现根集合内。[源码]
- 实际被加载的是隔离根 runtime/dsh-home/skills/material-writing 下的 SKILL.md，其内容与仓库内的同名文件逐字节一致（2996 字节）。[实测] 二者的一致来自既有的技能同步脚本，而不是 DSH 直接读取仓库。
- 同一目录下存在两个空目录（coding-agent、writing-agent），它们没有 SKILL.md，因此不会成为可用技能。[实测] 这一点与项目文档中"第一版只设计 5 个核心 Agent"的规划存在表面出入，但当前阶段不处理。

#### （2）用户通过 Web 界面提交写作任务时，是否存在明确可用的 Skill 调用路径？

结论：**存在两条官方路径，但都依赖技能被正确发现；接口本身可用。**[源码]

- 模型可调用：技能由工具按名称调用；若某技能声明为不可模型调用，工具会明确拒绝并提示「该技能不可用于模型调用」。[源码]
  > [!WARNING]
  > **已过时（Phase 2B 期间经源码核实更正）**：原表述「技能声明了 model-invocable」有误。
  > DSH 的 parseInvocationPolicy 只识别 kebab 键 disable-model-invocation 与 user-invocable；
  > 一旦写入 camelCase 键（modelInvocable / userInvocable / disableModelInvocation），**整个 Skill 会被静默忽略**；
  > 而 kebab 的 model-invocable 本身是**无效键**。
  > 详见 docs/OmniDesk-Phase2A-Report.md 第 56 节。
- 用户显式调用：工具会扫描用户消息的第一步，识别以斜杠加技能名开头的首行，从而强制启用该技能。[源码]
- 前端是否存在可见的技能选择控件尚未确认。[推断] 源码中存在一个技能相关的前端插件，但其呈现方式未在本次只读检查中确认。

因此，界面路径不是阻断点，阻断点在技能内部引用的资产解析上。

#### （3）Skill 能否正确找到模板、用户写作规则、输入素材和相关知识文件？

结论：**输入素材可以，模板与写作规则不能。**[源码 + 实测]

- 技能正文以相对路径引用三类资产：模板规范库、个人风格库、历史优秀范例。[源码]
- 技能被注入会话时附带的基准目录是技能自身所在目录，即隔离根下的 skills/material-writing，该目录内只有 SKILL.md。[实测]
- 按技能自身给出的解析规则（相对路径应相对基准目录解析），上述三类相对路径会落在隔离根内不存在的位置。[源码 + 实测]
- workstation 的 profile.yaml 中声明了 knowledge 指向家目录下 OmniDesk/knowledge，但该目录当前不存在。[实测] 家目录下的 OmniDesk 目前只有 runtime 一个子目录。
- 真实资产实际位于仓库：knowledge/writing-style、knowledge/excellent-cases、templates/discipline。[实测]

写入侧与读取侧指向不同位置，这是断链的直接成因。

#### （4）Skill 是否真的执行素材梳理、结构规划、起草、事实核对和成稿检查？

结论：**宣称了完整流水线，但执行条件不完整。**[源码 + 实测]

- 技能正文把流程描述为六步：素材解析、模板匹配、结构大纲、正文初稿、合规避坑审查、人工调整与反哺沉淀。[源码] 第 1 步含"明确读者对象与会议场景"，第 5 步含套话过滤与法规全称核验。
- 但第 2 步的表述是"自动确定适用的标准模板"，而模板库在运行时不可达，该步实际退化为凭记忆拟一个结构。[实测]
- 第 5 步要求对照避坑清单逐项自查，该清单同样不可达。[实测]
- 流程中**没有**独立的成稿后检查环节。仓库中已有独立的文档检查技能，但材料写作技能并未把它声明为必经步骤。[源码]

因此，即便输出看起来像六步流水线的产物，其中依赖本地资产的步骤并未真正执行。这一点与用户规则 9（初稿后独立检查）直接相关。

#### （5）生成结果是否保存到正确位置，是否存在原始素材被覆盖、引用丢失或结果不可追溯？

结论：**当前无任何落盘约定，属于未定义状态，风险实质存在。**[实测]

- 材料写作技能正文未声明输出目录或文件命名约定。[实测]
- 未声明禁止覆盖输入素材，也未声明引用来源必须回填。[实测]
- 记录文件规范存在（记录表含日期、任务、人工耗时、AI 耗时、修改次数、最终评价），但实际目录下只有说明文件，尚无任何记录。[实测]
- 结果的可追溯性依赖人工，缺少强制机制。

补充一个事实：存在一个脚本用于把外部制度原文转换为 Word 并同步进知识库，另有独立的知识引用审计报告。这说明"引用可追溯"在知识问答侧已有基础，只是在材料写作侧尚未接上。

#### （6）模型、Profile、Skill 和模板之间是否存在配置不一致？

结论：**模型与 Profile 一致；Skill 与模板、知识库之间不一致；仓库内部存在多份等价副本。**[实测]

| 项 | 观测 | 影响 |
| --- | --- | --- |
| 模型 | Profile 补丁层的默认模型与 provider 配置完整且被应用 | 无 |
| Profile 名称字段 | 隔离 Profile 的 package.json 中的 name 仍是通用占位名（dsh-profile-desktop） | 仅影响可读性，不影响加载 |

## 5. 最小实施步骤

排序原则：先修阻断项，再补规则，最后收敛结构。每一步都可独立提交、独立回归。

### Step 1（阻断）把技能同步接入启动路径

问题：技能同步脚本存在且防护完善，但启动器完全不引用它。每次修改仓库内的技能，都不会自动进入隔离根，实际加载的仍是旧副本。

动作：在启动器的启动流程中加入技能同步调用，使同步成为启动的一部分；或在启动前打印明确的必做步骤并在检测到不同步时拒绝启动。倾向前者，因为它消除人为遗漏。

涉及文件：scripts/omnidesk-dev.sh，可能需少量调整 scripts/sync-skills.sh。

风险：低。同步脚本已有空目录、软链接、目标越界的防护，且拒绝指向原版数据根。

### Step 2（阻断）锚定三类参考源

问题：技能正文以相对路径引用模板库、风格库、历史范例，而技能的基准目录内没有这三类内容，运行时无法解析。

三个候选做法，按推荐顺序：

- 2a（首选，官方机制）：通过 Profile 补丁把三个资产目录声明为自定义技能搜索目录。此处存在范围不确定性——顶层技能插件已被 Web Bundle 禁用、实际发现发生在预置内，顶层补丁未必能命中预置行。因此**实施前必须先用配置导出确认补丁是否真正影响发现点**，确认后再改。
- 2b（兜底，机制风险为零）：把被引用的资产复制进技能自身目录，使相对路径可解析。
- 2c（改动最小）：改写技能正文，改用仓库绝对路径引用，并补充一句"若目标不存在则跳过并说明"。

本阶段建议先采用 2c 保证链路可用，同时把 2a 作为后续目标，用配置导出记录结论。

涉及文件：skills/material-writing/SKILL.md；若走 2a 则加 profiles/yvan-work/cordis.patch.yml。

风险：中。2a 依赖尚未证实的补丁作用范围；2c 会把仓库路径硬编码进技能文本，需要在文档中记录这是过渡状态。

### Step 3（阻断）声明产出位置与来源回填

问题：技能未声明输出位置、未禁止覆盖输入素材、未要求回填引用来源。

动作：在技能正文中明确产出目录与文件命名；明确禁止覆盖输入素材；要求成稿末尾列出所引用的模板、风格条目与知识文件。

涉及文件：skills/material-writing/SKILL.md。

风险：低。

### Step 4 补齐六条未落实的写作规则

动作：按优先级补入规则 10（数据边界）、3（结构服从用途，需重写模板选择那一步）、6 与 11（缺证标注、存疑提问，建议合并为一条统一的"不确定即提问"约束）、5（已完成 / 推进中 / 计划 / 建议的分类要求）、7（保留用户自有措辞）。

风险：低。注意不要在风格库与技能正文两处写同一约束。

### Step 5 把成稿检查串联为必经步骤

动作：在技能流程末尾加入独立检查环节，复用现有的文档检查技能，检查维度覆盖结构、内容、表述、风险四项。
