## 1. 问题与已知事实

### 1.1 症状
在真实桌面手动试用主树与新 UI 时，用户报告「页面反应很慢」。

### 1.2 会话内观测（**原始输出未落盘，仅作线索，不作为验收基线**）

| 观测 | 值 |
| --- | --- |
| App 空闲停在首页时 `WebKitWebProcess` CPU | 约 **100%**（一个完整核）；App 自身 Rust 进程约 1.7%；网络进程 0% |
| debug+vite dev 对比 release+内嵌产物 | 空闲 CPU 约 **101.6% vs 102.0%**（瓶颈不在构建方式） |
| 导航延迟（含截图读回开销，仅相对参考） | 中位数 1.77 s vs 3.13 s |
| MiniBrowser 对照（同一一次性 Xvfb，`WEBKIT_DISABLE_DMABUF_RENDERER=1`） | 简单页 **0.0%**；复刻本应用特效层页面 **100.2%** |
| 同一特效页，DMABUF 打开 | **34.5%** |

**测量局限：** Xvfb 无 GPU / 无 DRI3；导航延迟测量含截图读回开销；均为单次运行。
**纪律：** 上述数字只说明「特效层与 DMABUF 都可能是成本来源」，**不得**据此把全部根因归给其中之一。
CSS 特效与 DMABUF 必须作为**两个独立变量**分别对照测量。

### 1.3 静态代码事实（候选触发因素清单）

| 位置 | 事实 |
| --- | --- |
| `desktop/src/App.tsx` | 三个 `fixed` 全屏渐变光斑，`blur-[120px] / [140px] / [130px]` |
| `desktop/src/shell/Dock.tsx`、`shell/TopNav.tsx` | `backdrop-blur-2xl`（约 40 px） |
| `desktop/src/theme.css` | `.plate-sculpted { backdrop-filter: blur(28px) saturate(170%) }` |
| `desktop/src/workbench-ui.css` | `.wb-v2 .pane { backdrop-filter: blur(20px) saturate(160%) }`（每个阶段卡片一层） |
| `desktop/src/offline-flows.css` | `.ofl-v2 .pane { backdrop-filter: blur(20px) saturate(160%) }`（每个面板一层） |
| `desktop/src/theme.css` | 无限动画：`.animate-pulse-ambient`(6 s)、`.animate-float-mascot`(5 s)、状态点 `animate-pulse` |
| `desktop/src/shell/TopNav.tsx` | 每 30 s `setInterval` → `setState`（整树重渲染） |
| `desktop/src/SettingsPanel.tsx` | 输入每次按键触发整面板重渲染（实测快速注入会丢字符） |
| `scripts/dev-ui.sh:361` | 默认 `WEBKIT_DISABLE_DMABUF_RENDERER=1`（原为规避「整屏发黑」） |

### 1.4 结论纪律
- 真实桌面在完成 Step 2–4 后若仍高占用，**继续用性能采样定位剩余原因**，不得以「已优化」结案。
- 任何一步的成功判定都必须同时满足：CPU **与**延迟/输入响应 **与**视觉观感，不能只看 CPU 下降。

## 2. 目标与非目标

### 2.1 目标（按优先级）
1. **首要：** 消除空闲时渲染进程持续占用一个 CPU 核的问题（稳定后不再持续高占用）。
2. 交互延迟相对基线明显下降；连续输入不丢字符。
3. 主要视觉层级、渐变与布局保留（不要「优化掉」产品观感）。

### 2.2 非目标（本轮不做）
- 不顺带重构 UI 架构、组件树、路由或设计体系；不做主题重做；不改信息架构与文案。
- **不全面删除玻璃特效**；不改变功能行为（本支线只动渲染成本）。
- 不做 OD-ARCH-026 的功能开发；不与 OD-ARCH-026 的复核混在一起提交。
- 不修改 `runtime/`、模型路由、凭证、真实材料、用户数据、第二 worktree；不提交/推送/打标签。
- 不做跨平台与系统级安装验证（另案）。

## 4. 执行顺序与阶段验收

> 严格分阶段，**不要一次性修改所有问题**；每一步都必须是可独立回退的最小改动。

### Step 0 证据归档（非阻塞，**已完成**）
- 输入：`/tmp` 中的原始脚本与数据。输出：`tests/verification/desktop/evidence/od-arch-027/`。
- 清点结果：**可复现脚本与对照页存在**（`od025-perf.py`/`perf2.py`/`perf3.py`、`baseline/simple.html`、`baseline/heavy.html`）；
  **原始结果输出未落盘**（仅存在于会话输出，已不可从 `/tmp` 取回）。
- 处置：按 §1.2 的记录归档脚本、对照页与环境事实；**不补造历史结果**；基线在 Step 2 重采并落盘。

### Step 1 建立计划（本文件，**已完成**）
- 验收：改动范围、依赖顺序、回退方式、验收阈值全部明确 → 本文件 §2–§7。

### Step 2 CSS 性能优化（P1；**待批准执行**）
- 输入：`desktop/src/App.tsx`、`theme.css`、`workbench-ui.css`、`offline-flows.css`、`shell/Dock.tsx`、`shell/TopNav.tsx` 的样式。
- 输出：低成本视觉效果实现——大半径模糊光斑改为静态渐变；减少**卡片级**叠加的 `backdrop-filter`；保留少量关键视觉层（如 Dock/顶栏其中之一或等价单一半透明层）。
- 约束：只改样式与既有类；不新增视觉体系；不改 JSX 结构与交互；顶层 `plate-sculpted` 若被替换，需在报告中说明替代观感。
- 验收：重采基线并对比——空闲 CPU、导航延迟 P50/P95、逐页前后截图；三页视觉层级仍清晰。
- 回退：还原上述样式文件；保留改动前数据与截图。

### Step 3 DMABUF 与显示后端独立对照（P1；零代码改动）
- 输入：相同构建、相同页面、不同渲染配置。
- 输出：可重复的对照数据（每项 ≥3 次运行）：默认配置 / `WEBKIT_DISABLE_DMABUF_RENDERER=0` / `GDK_BACKEND=x11`（XWayland）对比 Wayland。
- 验收：分别记录 CPU、导航延迟、输入响应与**画面异常**（黑屏/闪烁）；**不得仅凭 CPU 下降判定成功**；出现黑屏立即回退。
- 回退：DMABUF 为环境变量，即刻回退；若拟修改 `scripts/dev-ui.sh` 的默认值，须**单独批准**并保留旧默认。

### Step 4 无限动画与 React 重渲染治理（P2）
- 输入：Step 2/3 后的 UI 与性能采样。
- 输出：减少无效持续更新——收敛无限动画（含 `prefers-reduced-motion` 下的关闭）；缩小 `TopNav` 定时更新的重渲染范围；设置页输入不再触发整面板重渲染。
- 验收：空闲状态不再持续高占用；**设置页连续输入固定字符串全部正确、无丢字**。
- 回退：按文件还原；保留改动前采样与截图。

### Step 5 真实桌面回归验收（P3）
- 输入：最终构建与基线数据。输出：性能报告、截图、回退记录、证据索引。
- 验收：在真实 Wayland 桌面复测，确认 CPU、交互延迟与视觉效果均符合 §5；Xvfb 与真实桌面结果**分别记录**。
- **执行状态（2026-10-20，已执行）：** 在用户自己的 Wayland 会话（GNOME 50.1，`WAYLAND_DISPLAY=wayland-0`）完成四组实测：
  原生 Wayland × DMABUF{1,0} 与 XWayland × DMABUF{1,0}，**分别记录**。空闲 60 s 的
  `WebKitWebProcess` 均值 **0.08% / 0.17%（原生 Wayland）与 0.15% / 0.28%（XWayland）**，远低于
  §5 的 <10% 目标；导航 P50 0.31–1.22 s、P95 ≤1.63 s、0 超时；5 帧签名 = 1（无持续重绘）；
  设置页连续输入固定串**逐字落盘**（`exact_hit`）。原生 Wayland 的像素与合成输入通道在本机**不可用**
  （GNOME Screenshot D-Bus 被拒、Shell Eval 禁用、根窗口抓图为全黑），该部分指标由 XWayland 组单独提供。
  证据：`tests/verification/desktop/evidence/od-arch-027/README.md` §9 与 `step5/`。
- **结论纪律（不变）：** 原「空闲约 100%」的症状在真实桌面**同样没有复现**；本轮**不得**被表述为
  性能提升。Step 2/4 的产物是「症状不复现的当前状态」与「受控页面上该机制的量化证据」。

## 5. 验收阈值（首轮目标，**是目标不是保证**）

| 指标 | 首轮目标 | 口径 |
| --- | --- | --- |
| 空闲渲染进程 CPU | 稳定后 **60 s 平均 < 10%** | 只统计 `WebKitWebProcess`；同时记录 App 主进程与网络进程；`/proc/<pid>/stat` 的 utime+stime 增量 ÷ 墙钟 |
| 页面导航延迟 | 相比基线**明显下降**，记录 P50、P95 | 固定路径（首页→任务工作台→离线→设置→首页），每项 ≥5 次；标注截图读回开销 |
| 连续输入 | 固定测试字符**全部正确、无丢字** | 设置页输入框注入固定串后按文件/输入值比对 |
| 视觉效果 | Dock、顶栏、卡片层级清晰；主要渐变与布局保留 | 逐页前后截图对比 |
| DMABUF | 启用与禁用**分别记录**；黑屏可回退 | 单独变量，不与 CSS 改动同时施加 |
| 环境一致性 | Xvfb 与真实桌面**分别记录**，不混为一组 | 每组注明构建、数据根、显示后端、DMABUF 取值、窗口尺寸 |

> 若真实桌面在 Step 2–4 后仍高于目标，**不得改口径**；继续采样定位剩余原因并记录。

## 7. 风险与停止条件

- 若某一步需要修改 `runtime/`、模型路由、凭证、用户数据或第二 worktree → **停止该步并报告**。
