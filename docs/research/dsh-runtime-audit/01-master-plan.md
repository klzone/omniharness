# DSH Runtime 五阶段研究计划

- 状态：阶段一有条件通过；阶段二源码审计通过；阶段三未开始
- 原则：先版本基线，后源码审计；先机制证据，后对照实验；先归因，后决策
- 决策门禁：五阶段未完成前，不写“继续 DSH”“专用化改造 DSH”或“迁移 Pi”的结论

## 1. 阶段总表

| 阶段 | 进入条件 | 任务 | 交付物 | 验收标准 |
| --- | --- | --- | --- | --- |
| 一、版本与运行环境摸底 | 用户批准只读研究 | 六个只读任务卡：身份、来源、Profile、模型、历史证据、Pi 边界 | 正式基线、来源矩阵、Profile/插件摘要、模型路由摘要、证据适用性索引、Pi 边界 | 版本和来源不混淆；无源码时明确标记；Profile/模型均有路径和命令证据；未读取凭证或会话正文 |
| 二、六个机制源码审计 | 阶段一验收；G2 源码/产物审计基准确认 | 六张单动作审计卡，每张只审一个机制 | 五份核心机制报告 + 一份子 Agent 报告 + 初步架构图 | 每个结论关联文件、行号、入口/符号和运行观察；区分设计、实现、实跑；无证据的标 `U` |

## 2. 阶段一：版本与运行环境摸底

### 2.1 进入条件

- 用户已批准只读研究和研究文档编写。
- 已记录 Git 状态与 HEAD。
- 已区分“仓库锁定版本”“安装包版本”“当前运行版本”“参考版本”。

### 2.2 任务清单

1. 建立 Runtime 身份与版本矩阵。
2. 建立源码/gitlink/lock/运行产物来源图。
3. 建立 OmniDesk Profile 与插件装配摘要。
4. 建立模型路由与参数来源矩阵。
5. 建立历史文档/测试适用性索引。
6. 固定 Pi 研究对象边界与本机可用性。

### 2.3 交付物

- 正式 `00-baseline.md`
- `evidence/phase1/*.json|*.md`
- 研究负责人验收记录
- 阶段一补充任务清单（如有）

### 2.4 验收标准

- 四个身份全部可追溯：repo CLI、已安装 OmniDesk、当前 DSH Desktop、参考/候选 Pi。
- 每个版本都有来源路径和采集命令；不得把最新版本写成当前版本。
- rc.5 源码不可用必须有明确证据，不得凭 README 补全。
- Profile 选择、bundle 顺序、补丁层、插入插件和模型覆盖均有文件位置。
- 所有关键结论至少有一个 `F`、`S` 或 `R` 证据；`D` 不得单独作为行为证明。
- 不出现凭证值、会话正文、真实材料或完整敏感配置。

### 2.5 不进入阶段二的停止条件

- 找不到可审计的 rc.5 源码，且用户未批准编译产物审计。
- Profile 或模型路由的版本归属仍自相矛盾。
- 任务输出只是 README 复述，没有源码或运行证据。
- 执行过程中触碰 `runtime/`、凭证、会话正文或真实材料。

## 3. 阶段二：六个机制源码审计

### 3.1 进入条件

- 阶段一验收通过。
- 审计版本固定为 OmniDesk 的 rc.5；用户已选择方案 1。
- 精确源码已固定在 `/tmp/omnidesk-dsh-rc5-b830ec95.O48O03/repo`，commit `b830ec950faba0a46dda564be3e2d854afed94f1`，tag `dsh-v0.2.1-rc.5`。
- 审计存储位置在仓库外临时目录，不改 `runtime/`。

### 3.2 六张单动作审计卡

| ID | 单一动作 | 主要输入 | 交付物 |
| --- | --- | --- | --- |
| R2-01 | 追踪 System Prompt 的组装与请求序列化 | system-prompt、persona、agent-instructions、time-context、tools、llm-pi-ai | `system-prompt-assembly.md` |
| R2-02 | 追踪 Agent Loop 的轮次状态机 | agent-loop、agent、session、llm、tools | `agent-loop.md` |
| R2-03 | 追踪 Session Replay 与 Context Projection | session、session-persistence-jsonl、session-projection、compaction | `session-replay-projection.md` |
| R2-04 | 追踪 Tool Description 与 Schema 的注册、过滤、序列化 | tools、tool-fs、tool-web、tool-subagent、各工具包 | `tool-schema.md` |
| R2-05 | 追踪并行工具调度的决策、上限、顺序与取消 | agent-loop、tools、jobs、命令执行/网络工具 | `parallel-scheduler.md` |
| R2-06 | 追踪子 Agent 的创建、上下文、模型、工具、终态和回收 | tool-subagent、subagent-spawn-in-process、subagent-fork-in-process、workflow-ptc | `subagent-lifecycle.md` |

每张卡只允许一个机制动作。跨机制关系只在报告中登记，不顺手实现分析之外的代码检索。

### 3.3 交付物

- 五份核心模块审计报告和一份子 Agent 报告。
- 初步 DSH 核心架构图：入口、会话、prompt、loop、tool registry、scheduler、subagent、provider、持久化。
- 每个机制的“官方设计 / 当前实现 / 实跑表现”三列对照。

### 3.4 验收标准

- 每个关键结论至少关联一个文件路径和行号，或一个实际运行观察。
- 能回答“代码在哪里做决定”“输入从哪里来”“失败时怎样结束”“是否会持久化/重放”。
- 至少覆盖正常路径、空输入、工具失败、取消/中断、上下文超限和恢复路径中的适用项。
- 对无法静态证明的行为给出可执行验证方法和 `U` 标记。
- 不接受“DSH 是插件化的所以可定制”这类无代码位置的结论。

### 3.5 本轮结果

- 六份报告与初步架构图已完成，静态源码复核通过。
- 报告没有运行 build/test、Provider、服务或模型，因此只能支持静态机制结论。
- 详细复核见 [07-phase2-review.md](07-phase2-review.md)，架构图见 [08-dsh-core-architecture-map.md](08-dsh-core-architecture-map.md)。

## 4. 阶段三：DSH/Pi 同条件对照实验

### 4.1 进入条件

- 阶段二验收通过。
- Pi 研究对象固定：`pi-agent-core`、`pi-coding-agent` 或用户明确指定的 Pi 入口，以及确切 commit/包版本。
- 用户明确批准安装 Pi、启动真实模型和接触指定 Provider；此前的“禁止安装”仍然有效。
- 运行环境、模型 ID、Provider、参数、工具权限、任务集和终止条件已锁定。

### 4.2 任务清单

1. 写对照协议和变量清单。
2. 构造合成任务集与成功判据。
3. 对齐模型、Provider、温度/推理等级、最大输出、上下文上限、工具清单和权限。
4. 运行重复试验并保存原始请求/事件/usage。
5. 分别计算请求数、输入/缓存/输出/推理 Token、时延、工具调用数、失败与重试、上下文保真和任务完成。
6. 对照差异，做机制归因和反事实检查。

### 4.3 交付物

- `experiment-protocol.md`
- `fixtures/`（仅合成任务和脱敏数据）
- `run-ledger.json`
- `dsh-vs-pi-report.md`
- 原始记录索引与哈希

### 4.4 验收标准

- 两边模型、Provider、采样参数、工具定义和权限完全一致；任何差异都进入 `deviations`。
- 每轮至少重复次数、顺序、随机化和中止条件预先写明。
- 请求数与 Token 数分列；缓存命中、失败重试、人工中断分列；不得把“少请求”直接写成“性能更好”。
- 任务完成率使用预先定义的人工/脚本判定，不由模型自评代替。
- 每条差异至少绑定一条机制证据，不能只凭总体分数猜测。

## 5. 阶段四：问题归因与三层改造评估

### 5.1 进入条件

- 阶段三验收通过。
- 已有可重复的差异样例和原始证据。

### 5.2 任务清单

1. 建立症状、机制、根因、证据、置信度表。
2. 评估配置层改动的可行性与边界。
3. 评估插件层改动的可行性与版本兼容。
4. 评估源码 fork/补丁的可行性与维护成本。
5. 评估迁移 Pi 的功能缺口、数据迁移和工具对称性。

### 5.3 交付物

- 问题分类与根因分析。
- 配置/插件/源码改造可行性矩阵。
- DSH 专用化优化候选方案。
- Pi 迁移候选方案与阻塞项。

### 5.4 验收标准

- 每项根因都有阶段二或阶段三证据。
- 矩阵包含：改动层、改动对象、预期收益、证据强度、版本风险、回归范围、回滚方式、是否触碰产品边界。
- 不把候选写成已决定；不把“可修改”写成“应修改”。

## 6. 阶段五：最终技术决策与路线图

### 6.1 进入条件

- 阶段四验收通过。
- 用户参与对产品边界、维护成本和迁移风险的最后裁定。

### 6.2 决策选项

- 继续使用 DSH，维持版本与适配层边界。
- 专用化改造 DSH：仅配置/插件层，或进一步源码补丁/fork。
- 迁移 Pi：以 Pi Agent Runtime 为主，重建 OmniDesk 的会话、工具、权限和 UI 接缝。

### 6.3 交付物

- 最终 Runtime 技术决策。
- 实施路线图、验收门槛、回滚条件。
- 复审触发条件和未验证项。

### 6.4 验收标准

- 结论与证据链一一对应，包含反例和适用边界。
- 明确“继续使用”“专用化改造”“迁移”中的唯一主选择，不以模糊并行方案代替决策。
- 实施前仍需用户明确批准。

## 7. 跨阶段纪律

- 不把模型请求次数、Token 数量和任务完成率混为一谈。
- 不把 dump-config 可见写成模型实际收到。
- 不把历史 alpha.2 结论当作 rc.5 运行证据。
- 不把 Pi SDK 适配器当作 Pi Agent Runtime。
- 不把同一模型名称当作同一 Provider、参数或工具集。
- 不在没有用户授权时安装 Pi、读取凭证、启动真实模型或改动源码。
