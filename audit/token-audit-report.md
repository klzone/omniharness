## 结论

项目累计 Token 目前无法精确统计。可见的平台用量是账户级，不是项目级。历史审计摘要曾记录一个长线程约 5,394 次请求、输入约 4.37 亿 Token，但本次拿不到原始日志位置、筛选和任务归属，故不能把它或用户估计的“约 10 亿”当作 OmniDesk 已核实总量。

现有证据支持两类潜在消耗：长线程重复携带上下文；产品验收口径未前置，造成计划返工（OD-ARCH-025 不通过后重新校正至 026）。OD-ARCH-024 的多轮补测和性能排查中的完整验证有其质量价值，不能简单算作浪费。无效重试、截图过量、每类工作的准确 Token 份额均未证实。

## 最优先改进

1. 一个计划连续实施，阶段结束再集中验收；遇到阻塞或设计变化才重新规划。
2. 新阶段交接只带短状态摘要和精确文件范围，避免复制长历史。
3. 开发前明确用户可见的完成条件，避免 OD-ARCH-025 类方向问题到产品验收时才发现。
4. 保留必要最终全回归与独立 Review；成功输出只汇报摘要，失败时再查看最小日志。
5. 下一次试点开始/结束记录可映射到执行线程的真实用量；拿不到就报告未知，并用人工介入、返工轮数、耗时作辅助指标。

## 建议的下一阶段试点

用户已确认首页 UI 为当前定版方向，后续转入功能模块接入和 UI 微调。阶段二拟以一次集中任务完成三个模块接入，并以周报做首个真实桌面体验闭环；先完成 OD-ARCH-026 独立验收，再按计划边界实施。只使用合成或公开材料；用户指定 BUILDER 连续执行；ARCHITECT 最后集中检查源码、差异、测试和真实窗口证据。本报告本身不授权实施；当前具体范围见 PLANS.md 的 OD-ARCH-028。

记录指标：执行线程输入/输出/缓存 Token（仅当遥测能可靠映射时）、执行请求数、人工介入/澄清次数、返工轮数、实际耗时、必要测试通过情况和验收结果。与历史任务比较时同时说明工作规模和口径差异，不把单次试点泛化。
